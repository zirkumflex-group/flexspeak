# Memory optimization research — 2026-10-27

**Recommendation: measure graphics changes first.** The supplied observations are a few MiB of live Rust allocations, approximately 100–110 MiB RSS, and approximately 375 MiB macOS physical footprint after resizing, including about 255 MiB owned-unmapped graphics and 62 MiB IOSurface. These are inputs from the parent investigation, not measurements made for this report. They suggest graphics ownership deserves priority; they do not establish a leak or attribute the entire footprint to MSAA.

Scope: online primary documentation plus read-only inspection of this checkout and installed crate sources. Relevant resolved versions are Iced/iced_wgpu 0.14.0, iced_tiny_skia 0.14.1, wgpu 27.0.1, cryoglyph 0.1.0, cosmic-text 0.15.0 and Tokio 1.54.1. Rust requirement is 1.92. No application execution, builds, or performance tests were performed. **All proposed savings and performance effects below remain unmeasured for this app.**

**Keep the memory counters separate.** The local allocator wrapper forwards to `System` and counts requested Rust allocation sizes. It does not measure allocator slack, native-library allocations, thread stacks, or GPU resources. The pinned sysinfo macOS implementation reads `pti_resident_size`, so its process-memory value is RSS. Apple's VM Tracker and Metal Resource Events expose additional ownership: notably, Allocations alone excludes private-storage Metal resources. Do not add heap, RSS and physical footprint together, or subtract them to calculate a “leak.” ([Rust System](https://doc.rust-lang.org/std/alloc/struct.System.html), [sysinfo source](https://github.com/GuillaumeGomez/sysinfo/blob/97c194d6f0b0e09eee7db22e2128cd303e58a11d/src/unix/apple/macos/process.rs), [Apple memory analysis](https://developer.apple.com/documentation/xcode/analyzing-the-memory-usage-of-your-metal-app))

**Why the MSAA experiment is unusually promising here.** Iced's application AA setting maps to MSAA×4 for triangles. When triangles are present, the renderer supplies the **whole physical viewport** as the target size, even if a chart occupies a smaller region. Therefore reducing 300 samples to 150 would not halve these render targets. ([Settings conversion](https://github.com/iced-rs/iced/blob/0.14.0/graphics/src/settings.rs), [triangle preparation call](https://github.com/iced-rs/iced/blob/0.14.0/wgpu/src/lib.rs))

The MSAA implementation owns a multisampled attachment plus a single-sample resolve texture. It reuses them whenever both requested dimensions fit; shrinking the window alone therefore does not shrink them. If either dimension exceeds the allocation, it replaces the pair at the requested size. This is retained capacity, not evidence of unbounded accumulation. An upstream shrink policy would trade lower retained memory for reallocations and possible resize stalls; consider it only if AA must stay enabled and measurement warrants maintaining a patch. ([Iced 0.14 MSAA implementation](https://github.com/iced-rs/iced/blob/0.14.0/wgpu/src/triangle/msaa.rs))

For scale intuition only, assuming a four-byte color format, the pair's nominal texel storage is `physical_width × physical_height × 4 × (4 + 1)`. A 1200×800-point viewport at scale 2 gives about **73.2 MiB**, versus 18.3 MiB at scale 1, before drawables or driver allocation overhead. This arithmetic is not a predicted footprint delta: confirm actual formats, resource sizes and lifetimes. Retina doubles each dimension, quadrupling pixel area. Preserve display sharpness rather than forcing low-resolution rendering merely to improve the counter. ([MSAA texture descriptors](https://github.com/iced-rs/iced/blob/0.14.0/wgpu/src/triangle/msaa.rs), [Apple high-resolution model](https://developer.apple.com/library/archive/documentation/GraphicsAnimation/Conceptual/HighResolutionOSX/Explained/Explained.html))

Iced already requests `MemoryHints::MemoryUsage` and `desired_maximum_frame_latency=1`; recommending those again yields no change. Memory hints may be ignored, and frame latency is a backend-clamped hint, not a guarantee of one drawable. Leave presentation tuning alone for the initial A/B. ([Compositor](https://github.com/iced-rs/iced/blob/0.14.0/wgpu/src/window/compositor.rs), [wgpu hints](https://docs.rs/wgpu/27.0.1/wgpu/enum.MemoryHints.html), [surface configuration](https://docs.rs/wgpu-types/27.0.1/wgpu_types/struct.SurfaceConfiguration.html))

**Software rendering is a workload choice.** tiny-skia still has physical-pixel buffers, a clipping mask, and retained layer history. It performs damage tracking, so idle behavior does not imply full-window rasterization every frame. The current source accepts `tiny-skia` as a backend name. Test resize, scrolling, both tabs and concurrent voice; no feature removal is needed to run that comparison. Keeping both compiled backends does not mean two live renderers: the fallback renderer is an enum selecting one. Removing wgpu later also removes its fallback/acceleration option, so do that only after the runtime choice proves worthwhile. ([tiny-skia compositor](https://github.com/iced-rs/iced/blob/0ecf60664df7b8ac7d7aef5f7279d5323027f693/tiny_skia/src/window/compositor.rs), [fallback renderer](https://github.com/iced-rs/iced/blob/0.14.0/renderer/src/fallback.rs))

**Caches and fonts: reduce churn without sacrificing names or history.** Canvas caches retain generated geometry to avoid recomputation; `clear()` preserves the previous value for reuse. It is invalidation, not a reliable memory-release API. Grouping charts that change on the same tick is supported, but clearing them every frame defeats caching. Replacing/dropping a cache may release its own ownership; it does not promise to release the shared MSAA targets or immediately lower OS counters. ([Geometry cache](https://github.com/iced-rs/iced/blob/0.14.0/graphics/src/geometry/cache.rs), [underlying cache](https://github.com/iced-rs/iced/blob/0.14.0/graphics/src/cache.rs))

Text layout keys include content, font, size and bounds, and unused entries are trimmed. Fixed precision and stable label sizes are reasonable churn-reduction experiments; changing a numeric string is not proof of permanent accumulation. The actual GPU text dependency is **cryoglyph**, whose atlases start at 256×256, evict unused glyphs when necessary and grow; `trim()` resets usage bookkeeping rather than shrinking textures. Use resource evidence before inventing a font-cache limit. ([Text layout cache](https://github.com/iced-rs/iced/blob/0.14.0/graphics/src/text/cache.rs), [cryoglyph atlas](https://github.com/iced-rs/cryoglyph/blob/bb8f59f9f075267f44448e271c867b1278bfd849/src/text_atlas.rs))

Iced already shares a global font system. Load application fonts once; repeatedly loading owned font bytes is not deduplicated by the borrowed-byte address check. cosmic-text's `new_with_fonts` still loads system fonts, so bundling one font alone does not disable discovery/fallback. Removing that support risks missing glyphs in international server/user names; retain it absent compelling measurements. ([Iced font loading](https://github.com/iced-rs/iced/blob/0.14.0/graphics/src/text.rs), [cosmic-text 0.15 font system](https://github.com/pop-os/cosmic-text/blob/0.15.0/src/font/system.rs))

**Runtime and audio: protect deadlines.** Locally, the voice session already uses a current-thread runtime on its own thread. Iced's executor separately calls `Runtime::new()`, and its Tokio dependency enables `rt-multi-thread`. The worker-count experiment targets that pool; simply removing a direct Tokio feature will not undo a transitive feature. Do not substitute a current-thread GUI executor without arranging to drive it. ([Iced executor](https://github.com/iced-rs/iced/blob/0.14.0/futures/src/backend/native/tokio.rs), [Iced features](https://github.com/iced-rs/iced/blob/0.14.0/futures/Cargo.toml), [Cargo feature unification](https://doc.rust-lang.org/cargo/reference/features.html#feature-unification))

Tokio defaults to available parallelism and documents 2 MiB thread stacks. These reservations are not equivalent to committed RSS savings. Its default 512 blocking-thread limit is not 512 preallocated threads; lowering it is not an idle-memory fix and can stall blocking work. Inspect actual stack dirty/resident pages before changing stack sizes, especially across native calls where an undersized stack can fail. ([Tokio builder](https://docs.rs/tokio/1.54.1/tokio/runtime/struct.Builder.html), [Apple allocation versus footprint](https://developer.apple.com/documentation/xcode/analyzing-the-memory-usage-of-your-metal-app))

The app already reuses rubato buffers through `process_into_buffer()` and bypasses resampling at equal rates. Preserve these practices: that API is intended for allocation-free real-time processing. Smaller chunks trade buffer memory/latency against processing overhead; replacing sinc with an unfiltered resampler trades sound quality for speed. Neither is justified by the present graphics-heavy evidence. ([rubato 0.16.2 guidance](https://docs.rs/rubato/0.16.2/rubato/))

CPAL runs callbacks on audio delivery threads; keep allocation, blocking work and diagnostics outside normal callbacks. A smaller requested device buffer lowers latency but can raise CPU and dropout risk, and the actual callback size may differ. Retain bounded queues; distinguish **capacity** from occupied audio latency. The local quarter-second capture/playback queues hold only about 141 KiB of sample payload at 48 kHz, plus queue metadata, so trimming these is a low-priority RAM intervention. ([CPAL threading](https://docs.rs/cpal/0.18.2/cpal/), [buffer tradeoffs](https://docs.rs/cpal/0.18.2/cpal/enum.BufferSize.html), [fixed-capacity queue behavior](https://docs.rs/crossbeam-queue/0.3.14/crossbeam_queue/struct.ArrayQueue.html))

Reuse Opus state per stream; do not reinitialize it per packet. Its `create`/`destroy` APIs own native allocations, so inspect those separately from the Rust counter, especially across reconnects. No codec-quality reduction is proposed. ([Official Opus API](https://opus-codec.org/docs/opus_api-1.5/group__opus__encoder.html))

**Allocator alternatives are conditional, not a first fix.** The current tracked allocator explicitly uses System. For an eventual A/B, route the existing accounting wrapper consistently through either System, a Rust-compatible mimalloc wrapper, or tikv-jemallocator; pin a release compatible with Rust 1.92 and check which native allocator it vendors. A Rust global allocator does not automatically redirect libopus/CoreAudio/Metal allocations. Keep ownership paired across FFI: free native objects with their native destructor, and Rust objects through their originating allocator. Even System pointers are not universally interchangeable with raw `malloc`/`free` because of alignment handling. ([System contract](https://doc.rust-lang.org/std/alloc/struct.System.html), [mimalloc wrapper](https://docs.rs/mimalloc/0.1.52/mimalloc/), [jemallocator integration/platform support](https://github.com/tikv/jemallocator))

More aggressive mimalloc purging can reduce retained pages at a performance cost. Jemalloc likewise exposes decay and arena-count tradeoffs: fewer arenas can reduce fragmentation but increase contention. Start with defaults; do not copy Linux purge/huge-page settings onto macOS. Jemalloc background purging is platform-dependent, and macOS-wide mimalloc interposition is a separate integration subject to security restrictions and mixed-heap hazards. No allocator promises to remove live graphics resources. ([mimalloc options](https://github.com/microsoft/mimalloc/blob/v3.6.0/readme.md#environment-options), [jemalloc tuning](https://github.com/jemalloc/jemalloc/blob/dev/TUNING.md), [platform-dependent controls](https://jemalloc.net/jemalloc.3.html#background_thread), [macOS/interposition cautions](https://microsoft.github.io/mimalloc/overrides.html))

**Build flags and features: do not confuse file size with RAM.** Keep thin LTO and the present release optimization as baseline. `opt-level="s"`/`"z"`, fat LTO, fewer codegen units, `panic="abort"`, or stripping more symbols may change binary size or generated code; none guarantees lower runtime RSS or GPU footprint. In particular, `"z"` disables loop vectorization, and abort changes failure behavior and prevents unwind recovery. Preserve useful symbols in a separate profiling artifact. Compare CPU/audio deadlines if testing code-generation changes. ([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html))

The manifest already disables defaults for Iced, rubato, sysinfo and tsclientlib. Audit resolved, target-specific features with `cargo tree --locked --offline --target <actual-target> -e features`, then inverse queries such as `-i tokio`; dependency count alone is not resident-memory evidence. Keep `canvas` for charts and ReSpeak `audio` for voice. The pinned ReSpeak manifest already allows disabling its default TLS bundle. Removing Linux window-system support is a portability change, not an assumed macOS RAM saving. Features are additive, so verify the entire graph before claiming a feature is absent. ([Cargo feature inspection](https://doc.rust-lang.org/cargo/reference/features.html#inspecting-resolved-features), [pinned ReSpeak manifest](https://github.com/ReSpeak/tsclientlib/blob/ee3bc6f45a7137db7793ba5593a321df400d53e5/tsclientlib/Cargo.toml))

Keep the existing bounded 300-point histories, one-second process sampling, lazy 20,000-event recorder and streaming export as the baseline. Reducing their limits would remove useful history/trace coverage without explaining the reported graphics ownership. This is a prioritization judgment based on the supplied measurements, not a claim that these features are free.

**Minimal measurement plan for the parent — proposed, not executed:**

1. Fix release revision, hardware, display/backing scale, window dimensions and audio workload. Use fresh processes for baseline wgpu+AA, wgpu without AA, and tiny-skia; repeat each three times. Visit Voice and Statistics in the same order, then small → large → small window sizes, pausing equally at each step. Include a fresh-small launch to expose retained resize capacity.
2. At matching checkpoints record Rust live/peak bytes, RSS, physical footprint and `vmmap -summary <pid>` categories, including MALLOC, stacks, IOSurface and owned-unmapped graphics. Record current versus peak separately. Use Instruments VM Tracker plus Metal Resource Events to find `iced_wgpu::triangle::msaa attachment`, its resolve target, and `glyphon atlas` allocations. Apple's Game Memory workflow combines these instruments; heap Allocations alone is insufficient. ([Apple Metal memory tools](https://developer.apple.com/documentation/xcode/analyzing-the-memory-usage-of-your-metal-app), [Apple vmmap/heap workflow](https://developer.apple.com/videos/play/wwdc2022/10106/))
3. Compare idle and active CPU, frame/update latency, audio callback/decode/encode tail latency, underruns and reconnect behavior. Test 44.1↔48 kHz resampling, multiple speakers and resize during playback. Accept savings only with acceptable chart rendering, Unicode names and voice behavior. These are proposed acceptance checks, not established performance results.
4. Keep tracing off for baseline; separately measure first recording, bounded-buffer saturation, export and post-export idle. For unexplained retained malloc memory, use Allocations generations/Leaks and malloc stack logging in a separate diagnostic run, then repeat the winner without instrumentation. Apple documents stack-logging-assisted `heap`, `malloc_history` and `leaks` analysis. ([Apple profiling workflow](https://developer.apple.com/videos/play/wwdc2022/10106/))

No unreleased framework switch is recommended. Any future Iced/wgpu branch experiment should be isolated, pinned and treated as an API/MSRV/rendering-regression risk; a main-branch claim is not evidence that a fix exists in this lockfile.
